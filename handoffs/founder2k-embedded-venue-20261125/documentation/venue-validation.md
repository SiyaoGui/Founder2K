## 六个现场场景

| 场景 | 实际执行及观察 |
|---|---|
| 1. 两组逐一交棒 | 两组的接收端同时解码演示画面、收到 440 Hz 主持人音频。A 交棒后，伙伴只收到一条 880 Hz 私聊音轨，演示画面消失。此时 B 仍能解码演示画面，只有一条音轨，主频仍为 440 Hz。一分钟后才向 B 发出交棒命令。两组均按预期切换。 |
| 2. 发起人等人 | 浏览器实际等待 121 秒。总主持人的房间数据超过 120 秒告警阈值，发起人的议程显示对方尚未签到。成员可登记补谈请求。 |
| 3. 提前结束和下一场冲突 | 两对先分别占位。一对结束后，另一对继续。单方同意未能提前入场。双方离开上一场、分别同意后，服务端放行。逐项比较确认六轮原计划时间均保留。 |
| 4. 六场议程中的变动 | 390 × 844 视口可展开六行议程，页面没有横向滚动。另测撤回预约后显示空档并保留已完成记录、原地址刷新恢复当前阶段、换设备后旧设备操作失效，以及调度后双方读到同一时间。各步骤分别验证，真人连续完成六场的可用性待测。 |
| 5. 双运营并发 | 主持人与另一名已获本场调度权限的测试成员，同时用同一版本调整同一预约。结果为一个 HTTP 200、一个 409。调度员召回全场被拒，撤销调度权限后再调整也被拒。未报名身份无权读取会场，观众不能申请团队房媒体。真实旁听设备使用已保存旧链接的端到端测试待做。 |
| 6. 召回、离场、续期、组队 | 文字通知期间 B 继续收看。召回后 B 收到新演示轨道。主动离场后签到状态取消，媒体授权被拒。对开始时间距今四小时的活动，等短期票据实际到期后成功重新取得只读票据。双方按原活动流程完成邀请、接受及审核，成员从主站工作台接口读取到新团队。 |

总主持人创建的私密彩排沿用原报名权限和六位会面对象。测试核对了彩排独立签到、通知只在对应实例可见、普通成员无权创建彩排、未报名者无权进入。快闪、导师答疑及路演分别通过活动模式接口检查。

## 快闪团队与并行讨论

- 主持人通过浏览器全选有 idea 的成员、Builder、Seller，生成草稿并发布。未发布时成员安排保持原值。测试验证了每组一个发起人、Builder 数相差 1、两组各一个 Seller。成员看不到完整编组名单，另一个版本的调度请求被拒绝。
- 主持人留在主会场发送演示和 440 Hz 测试音，同时两个团队分别开始讨论。用三个接收端在同一阶段验证主会场有画面并收到 440 Hz，两间讨论组分别只有一条音轨，主频为 660 Hz 和 880 Hz。其中一位接收者使用 390 像素手机视口。
- 将一名 Builder 的姓名从原组拖到另一组，确认发布后该成员读到目标组的媒体授权；原组的媒体房间标识已更新，目标组保留原媒体房间。原组重新打开麦克风后听到正确音频。
- 单独使用 100 名合成成员创建 20 个团队，服务端确认每组 1 位有 idea 的成员、2 位 Builder、2 位 Seller。在一个 Chromium 测试客户端中建立 40 条已授权 WebRTC 成员连接，每组 1 发、1 收，共 20 个独立媒体房间。所有接收端在同一次检测中只有一名远端成员、一条音轨，并测到本组指定频率。该次测试只发音频、使用回环网络。100 路同时发流、公网、真机和持续 4 小时仍待测。新增媒体供应商费用 $0。
